## ۲. چشم‌انداز و اهداف اصلی

- تولید چارت و گزارش قابل بازتولید از تاریخ، زمان و مکان تولد.
- شخصی‌سازی خروجی با تنظیمات محاسباتی، میزان قطعیت ساعت تولد، زبان و موضوع مورد درخواست.
- نمایش ارتباط روشن بین داده چارت، قاعده تفسیری و متن گزارش.
- ارائه رابط فارسی راست‌به‌چپ برای چارت ودیک، جدول موقعیت‌ها، مقایسه دو چارت و خط زمانی ترانزیت.
- حفظ مالکیت کاربران بر پروفایل‌های تولد، گزارش‌ها و مجوزهای اشتراک‌گذاری.
- سنجش صحت نجومی با آزمون محاسبات؛ سنجش کیفیت تفسیر با بازبینی محتوا و بازخورد کاربران به‌صورت جداگانه.

| MVP — محدود | سیناستری دو پروفایل با قواعد مشخص؛ ترانزیت بازه حداکثر ۹۰ روز برای سیارات تعریف‌شده |

| نسخه بعدی | اشتراک، پرداخت، اعلان ترانزیت، اپلیکیشن موبایل و دستیار متنی اختیاری |
| خارج از دامنه اولیه | اصلاح خودکار ساعت تولد، شبکه اجتماعی، بازار مشاوران و پیش‌بینی قطعی رویدادها |

- انتشار پرداخت و اشتراک به انتخاب بازار، ارائه‌دهنده و تعریف محصول تجاری وابسته است؛ در برنامه ۲۴ هفته‌ای الزامی نیست.
- دریافت جنسیت، شغل یا اطلاعات مالی فقط برای قابلیت مشخص و اختیاری انجام شود؛ این داده‌ها ورودی محاسبه موقعیت نجومی نیستند.
- در نبود ساعت تولد، محصول خروجی محدود ارائه دهد؛ طالع، خانه‌ها و نمودارهای حساس به زمان بدون مبنای معتبر تولید نشوند.

## ۴. معماری کلان

| لایه | مسئولیت و انتخاب پیشنهادی |
| --- | --- |
| رابط کاربر | TypeScript/React؛ SVG برای چارت؛ RTL، طراحی واکنش‌گرا و نمایش فارسی |
| API و منطق محصول | Python/FastAPI؛ بک‌اند ماژولار با قرارداد OpenAPI |
| موتور نجومی | آداپتور Swiss Ephemeris در پردازشگر جدا؛ ورودی و خروجی ساختاریافته و نسخه‌دار |
| زمان و مکان | پایگاه شهرها، مختصات، شناسه منطقه زمانی IANA و تبدیل تقویم؛ داده جغرافیایی در PostgreSQL/PostGIS |
| قواعد ودیک | ماژول مستقل ناکشاترا، وارگا، داشا و قواعد سیناستری |
| تفسیر | قواعد و متن‌های بازبینی‌شده با شناسه منبع، نسخه و پیوند به شواهد چارت |
| داده اصلی | PostgreSQL برای کاربران، پروفایل‌ها، محاسبات، گزارش‌ها و مجوزها |
| پردازش غیرهم‌زمان | Redis و صف پایدار برای گزارش، PDF و جست‌وجوی رویدادهای ترانزیت؛ Retry و Idempotency |
| فایل و عملیات | ذخیره‌سازی سازگار با S3، لینک محدود، لاگ ساختاریافته، متریک و ردیابی |
| انتشار | کانتینر، CI/CD و محیط‌های جداگانه توسعه، آزمایش و تولید |

- مسیر پردازش: دریافت تولد ← اعتبارسنجی ← تعیین مکان و منطقه زمانی ← رفع ابهام زمان ← UTC/UT1/TT ← محاسبات نجومی ← قواعد ودیک ← تفسیر ← نمایش و گزارش.
- قرارداد موتور شامل طول دایرةالبروجی، عرض، فاصله، سرعت، طالع، خانه‌ها و خطاهای ساختاریافته باشد.
- حالت‌های جهانی موتور، مانند آیانامشا و مختصات ناظر، در Workerها ایزوله شوند؛ درخواست‌های هم‌زمان تنظیمات یکدیگر را تغییر ندهند.
- در MVP، API یک استقرار ماژولار داشته باشد؛ تفکیک بیشتر سرویس‌ها به شواهد بار و نیاز عملیاتی وابسته باشد.
- هوش مصنوعی احتمالی فقط متن را بر اساس داده تأییدشده تولید کند؛ تولید درجات، طالع یا تاریخ دوره‌ها در اختیار موتور قطعی باقی بماند.

## ۵. الزامات کیفیت و معیارهای پذیرش کلان

**تمام اعداد این بخش هدف طراحی هستند و باید در فازهای ۱ و ۱۰ تثبیت شوند.**

| حوزه | هدف پذیرش |
| --- | --- |
| دقت موقعیت‌ها | اختلاف حداکثر ۱ ثانیه قوسی با اجرای مرجع مستقل Swiss Ephemeris، با نسخه، داده و تنظیمات یکسان |
| طالع و خانه‌ها | اختلاف حداکثر ۵ ثانیه قوسی در نمونه‌های معتبر؛ سناریوهای تعریف‌ناپذیر با وضعیت صریح |
| زمان و قواعد | عبور کامل آزمون‌های زمان مبهم/ناموجود، تقویم، مرز برج، وارگا و داشا |
| کارایی | p95 محاسبه D1+D9 زیر ۲ ثانیه با Cache خاموش، در آزمون ۱۰ درخواست در ثانیه برای ۳۰ دقیقه روی سخت‌افزار ثبت‌شده |
| گزارش | تکمیل ۹۵٪ گزارش‌های استاندارد تا ۶۰ ثانیه، با صف ۲۰ کار هم‌زمان |
| دسترس‌پذیری خدمت | SLO ماهانه ۹۹٫۵٪ برای APIهای اصلی؛ تعریف دقیق نقطه سنجش و بودجه خطا در فاز ۱۱ |
| بازیابی | RPO حداکثر ۲۴ ساعت؛ RTO حداکثر ۴ ساعت؛ همراه با تمرین Restore |
| امنیت | نبود نقص بحرانی/شدید باز در انتشار و عبور آزمون دسترسی بین کاربران |
| رابط | مسیرهای اصلی با صفحه‌کلید و صفحه‌خوان؛ هدف WCAG 2.2 AA و PDF فارسی خوانا |
| بازتولیدپذیری | بازاجرای ورودی و نسخه‌های ثابت، خروجی همسان در دقت ذخیره‌سازی تولید کند |

- مقایسه با اجرای مرجع همان کتابخانه، صحت ادغام را می‌سنجد؛ صحت مستقل نجومی با مجموعه داده ثانویه و مختصات/مقیاس زمانی یکسان بررسی شود.
- قرارداد تحمل خطا برای داده ثانویه در فاز ۲ تعریف شود؛ منابع ناهمسان بدون همسان‌سازی مقایسه نشوند.

## ۶. مدیریت اجرا، اسناد و تغییرات

- شناسه‌ها: نیازمندی `REQ-xxx`، فاز `AST-Pxx`، تسک `Pxx-Tyy`، تصمیم `ADR-xxx` و آزمون `TEST-xxx`.
- هر تسک: شرح، مالک، اولویت، وابستگی، تخمین، معیار پذیرش و پیوند به Pull Request.
- ماتریس ردیابی: نیازمندی ← تسک ← تصمیم معماری ← آزمون ← خروجی فاز.
- اسپرینت دو هفته‌ای؛ برنامه‌ریزی، جلسه کوتاه روزانه، بازبینی و بازنگری در پایان اسپرینت.
- Definition of Ready: ورودی، وابستگی، نمونه و معیار پذیرش روشن.
- Definition of Done: بازبینی کد/محتوا، آزمون متناسب، مستندات، ثبت نسخه و پذیرش مالک خروجی.
- تغییر دامنه: ثبت اثر بر زمان، هزینه، دقت و امنیت؛ تصمیم مالک محصول؛ به‌روزرسانی هم‌زمان سند مادر و سند فاز.
- بودجه: هزینه نقش‌ها بر اساس ظرفیت واقعی + مجوزها + داده/Geocoding + زیرساخت + بازبینی امنیت + ذخیره پیشنهادی ۱۵٪.
- وضعیت فازها: برنامه‌ریزی‌شده، در حال اجرا، در بازبینی، پذیرفته‌شده؛ پذیرش هر فاز با شواهد ثبت شود.
